# План миграции PalletLab на веб-стек

## Статус и цель

Этот документ описывает миграцию текущего Windows-приложения PalletLab с
PyQt5/PyVista на React/TypeScript, pywebview и Three.js. Миграция выполняется
в ветке `feat/web-migration`, созданной от актуальной `dev`.

Цель следующего публичного релиза — сохранить весь существующий функционал,
перевести его на новый стек, подтвердить функциональный паритет и только затем
применить готовый дизайн из Figma. До финального релиза пользовательская версия
на PyQt5 остаётся действующей.

## Принятые решения

- Платформа: Windows.
- UI: React + TypeScript + Vite внутри pywebview.
- 3D: Three.js через React Three Fiber.
- Логика и расчёт: существующий Python core сохраняется.
- STEP: существующий Python/OpenCascade конвейер сохраняется и отделяется от Qt.
- CAD: текущие Python COM-экспортёры и C# SolidWorksDrawingHelper сохраняются.
- Взаимодействие UI и Python: pywebview JavaScript-Python bridge, без FastAPI.
- Поставка: как и сейчас, installer и portable-сборка; рядом с исполняемым
  файлом допустимы нужные ресурсы и компоненты.
- Git: Conventional Commits; не выполнять push, merge, тегирование или выпуск
  релиза без отдельного указания.

## Неподвижные границы

1. Расчётная геометрия остаётся единственным источником истины. React не
   вычисляет и не валидирует конструкцию поддона самостоятельно.
2. Формат проектов `.palletlab.json` остаётся совместимым с ранее сохранёнными
   проектами, если явно не будет утверждён процесс миграции формата.
3. STEP-импорт не теряет кэш, прогресс, поддержку наклонных плоскостей и выбор
   опорных граней.
4. Экспорт сохраняет нативные результаты: `.SLDPRT`, `.SLDASM`, `.SLDDRW`,
   `.m3d`, `.a3d` и связанные чертежи. SolidWorks и КОМПАС-3D по-прежнему
   должны быть установлены у пользователя.
5. Главная миграция не добавляет новые продуктовые возможности. Редизайн
   начинается лишь после подтверждённого функционального паритета.

## Целевая архитектура

```text
PalletLab
├── frontend/                         React, TypeScript, Vite, Three.js
│   ├── application shell
│   ├── forms and dialogs
│   ├── typed bridge client
│   └── 3D viewport
├── src/palletlab/
│   ├── core/                         existing calculation and persistence
│   ├── application/                  UI-independent use cases and bridge API
│   ├── importers/                    STEP parsing and support detection
│   ├── exporters/                    CAD integrations
│   └── desktop/                      pywebview startup and packaging helpers
└── tools/SolidWorksDrawingHelper/    native SolidWorks drawing helper
```

Python exposes commands and snapshots through a narrow, typed bridge. The
frontend renders returned state and requests commands. Long-running actions
(STEP import, CAD export, updates) report progress and completion through a
single event mechanism. Browser components never call COM, OpenCascade or file
system APIs directly.

## Модель обмена данными

Перед переносом экранов должны быть определены и покрыты тестами JSON DTO:

- `ProjectSnapshot`: входные параметры, слои, материал, настройки вида,
  активный инструмент, сохранённое состояние проекта;
- `PalletSnapshot`: балки, габариты, размеры, точки вставки, редактируемые
  элементы и камера;
- `ImportedModelSnapshot`: подготовленная STEP-сетка, идентификаторы граней,
  ориентация и найденные опоры;
- `CommandResult`: обновлённые снимки, пользовательская ошибка и метаданные;
- `OperationProgress`: идентификатор задачи, стадия, процент и итог.

Для STEP-сеток требуется отдельный двоичный или файловый маршрут передачи,
если JSON окажется слишком тяжёлым. Решение принимается после измерения на
реальных моделях; идентификатор исходной CAD-грани обязан сохраняться в любом
варианте.

## Этапы

### 0. Базовая фиксация и измерения

- Зафиксировать начальную ревизию и создать таблицу функционального паритета.
- Прогнать существующий test suite и отметить тесты, требующие установленного
  CAD либо OpenGL.
- Сохранить примеры проектов и STEP-моделей для ручной регрессии.
- Измерить размеры типичных STEP-сеток и время импорта/рендера.

Результат: воспроизводимый baseline и список критериев приёмки миграции.

### 1. Application layer и bridge-контракты

- Вынести из `MainWindow` сценарии в UI-независимые application services.
- Сохранить `core`, контроллеры и экспортёры как доменную основу; заменить
  зависимости от Qt на простые callbacks, события или адаптеры.
- Ввести DTO и сериализацию с явной валидацией входа на Python-границе.
- Написать unit-тесты команд без запуска pywebview.

Результат: Python API, который можно вызвать как из текущего Qt UI, так и из
будущего React UI.

### 2. Минимальный desktop host и frontend shell

- Добавить React/TypeScript-проект, сборку и линтеры.
- Добавить pywebview startup, загрузку локальных frontend assets и bridge.
- Реализовать typed client, базовый layout и обработку ошибок.
- Открыть приложение, вызвать тестовую команду Python и отобразить ответ.

Результат: локальное окно React внутри Python-приложения без HTTP backend.

### 3. Функциональный перенос 2D-интерфейса

- Перенести формы расчёта, правила округления и выбор материала.
- Перенести слои, пользовательские сечения, сохранение/открытие,
  автосохранение, undo/redo и Reset.
- Сохранить debounce и поведение при ошибках расчёта.
- Перенести диалоги файлов, прогресс и сообщения, используя системные диалоги
  там, где это нужно для Windows UX.

Результат: React UI может полностью вести проект без 3D-инструментов.

### 4. Three.js viewport

- Визуализировать балки, материал, слои и размерные аннотации.
- Реализовать камеры: изометрия, сверху, спереди, сбоку и вписать.
- Перенести точки вставки, preview вставки, выбор/удаление брусьев и изменение
  расстояний/сечений.
- Сохранять и восстанавливать состояние камеры в проекте.
- Проверить управление мышью, DPI 125–150%, производительность и отсутствие
  самопроизвольного сброса камеры.

Результат: замена PyVista viewport для ручного проектирования.

### 5. STEP workflow

- Подключить существующий worker, протокол прогресса и локальный кэш.
- Передавать в Three.js сетку вместе с отображением CAD-face ID → mesh faces.
- Воссоздать показ импортированной модели, hover, выбор базовой грани,
  подсветку опор и перестроение паллеты.
- Проверить отмену, ошибки импорта и повторное использование кэша.

Результат: полный STEP-сценарий без PyVista/Qt.

### 6. Экспорт и чертежи

- Подключить команды SolidWorks и КОМПАС к application layer.
- Перенести в React выбор папок, шаблонов, библиотеки материалов и объёма
  чертежей.
- Оставить COM-операции на Python-стороне, показать прогресс/ошибки в UI.
- Настроить воспроизводимую Release-публикацию C# helper и добавить её в
  package manifest.
- Проверить на машинах с реальными SolidWorks и КОМПАС-3D.

Результат: тот же CAD-вывод из нового UI.

### 7. Поставка, обновление и полный паритет

- Обновить PyInstaller spec, зависимости, installer и CI build.
- Сохранить portable и installer каналы, проверить обновление установленной
  версии.
- Убрать Qt/PyVista только после прохождения полного паритета.
- Прогнать unit, integration, UI smoke и ручный acceptance checklist.

Результат: функционально готовая миграция, ещё с временным визуальным слоем.

### 8. Применение Figma-дизайна

- Реализовать готовый дизайн на уже стабильных React-компонентах.
- Добавить анимации, тени и переходы без изменения бизнес-контрактов.
- Сверить экраны с Figma и повторить полный регрессионный набор.

Результат: готовый к выпуску новый интерфейс и новый стек.

## Критерии готовности к финальному релизу

- Все поддерживаемые пользовательские сценарии имеют функциональный паритет.
- Существующие Python unit-тесты проходят; добавлены тесты bridge и frontend.
- STEP импорт, выбор опор и интерактивный 3D протестированы на реальном
  Windows desktop, а не только в unit-тестах.
- Проверены экспорты и чертежи в установленном SolidWorks и КОМПАС-3D.
- Installer и portable-сборка работают на чистой Windows-машине.
- Старые `.palletlab.json` открываются корректно.
- Новая UI-реализация соответствует предоставленному Figma-дизайну.

## Правила выполнения

- Каждый коммит использует Conventional Commits и объединяет только одно
  существенное, связанное изменение.
- Перед коммитом выполняются релевантные проверки и фиксируется их результат.
- Не выполнять push, merge, тегирование или создание релиза без явного
  запроса.
- Не удалять рабочий PyQt путь, пока React-замена не покрыта проверками.
